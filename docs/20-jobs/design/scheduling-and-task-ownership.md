# 调度和任务所有权

原文决策来源：commit c9299f168b7566f9d188017acc16e08f8ad6b43b，openspec/changes/archive/2026-07-25-configure-scheduled-producers/design.md、2026-07-28-unify-job-trigger-entrypoints/design.md。当前边界以 jobs 模块规格为准。

## 关键取舍

### 逻辑槽账本作为调度事实

- 背景：仅依赖进程内定时器无法可靠处理重启、并发检查和错过触发。
- 决策：在数据库事务内记录生产者逻辑槽和创建的任务，以稳定键保证同槽幂等。
- 否决方案：外部 cron、进程内事件或重启后重复扫描补发。
- 约束：Scheduler 不调用上游或认领业务任务；时区与槽标识需有稳定语义。
- 重新评估：部署从单机 SQLite 转为多个调度节点时，先确认数据库事务、锁和唯一约束仍能提供单槽原子性。

### 固定消费者按 Job 类型隔离

- 背景：实时采集有短周期时效要求，历史补采、作者回填和导出可能长时间运行。
- 决策：消费者由固定 Job 类型白名单定义，实时与人工队列分离。
- 否决方案：所有 Worker 竞争一个通用队列，再由 handler 判断归属。
- 约束：每一类 SQLite 消费职责单实例；新增 Job 类型须评审生产者、唯一消费者和终态语义。
- 重新评估：若数据库后端和容量模型支持同类多消费者，先验证锁、幂等与 checkpoint，再扩容。


### 生产者错过触发与重叠处理必须有界

- 背景：停机或规则暂停后可能积累大量过期时间槽；无限补跑会造成来源突发访问并阻塞实时队列。
- 决策：每条代码注册规则声明受限的 misfire 和 overlap 策略；调和循环只处理上限内的槽并记录被跳过/合并的逻辑槽。
- 否决方案：恢复后无界枚举历史槽，或以进程轮询频率作为业务调度频率。
- 约束：逻辑槽去重键稳定；规则暂停只阻止未来自动入队，不取消已存在任务。
- 重新评估：业务明确要求补齐更长历史窗口时，以显式人工范围 Job 实现，不放宽 Scheduler 的无界补跑。
