# 文档维护与决策分级

## 核心理念

代码表达“怎么做”，OpenSpec 表达系统“做什么”，design 只保留为什么这样做、跨模块边界、不变量和外部约束。每类信息只维护一个权威位置；其他文档链接权威来源，不复制定义。

目录按仓库代码模块组织，统一使用两位数字前缀。文档类型为 design/、api/、integration/、runbooks/；没有资料的类型不建。模块 README 是入口，登记主规格、代码入口、文档和未关闭缺口。

## 真相源

| 内容 | 权威位置 |
| --- | --- |
| 当前验收行为 | openspec/specs/{module}/spec.md |
| 当前实现事实 | 源码、migrations、测试 |
| 关键取舍与无法由实现还原的不变量 | 对应模块 design/ |
| 精确接口字段契约 | 对应模块 api/；私有上游观察归 integration/，不宣称正式契约 |
| 可重复执行的操作与验证方案 | runbooks/ |
| 单次验证的实际结果 | 对应 OpenSpec tasks、发布或演练记录；不得把计划写成已通过 |

## L0 / L1 / L2

| 级别 | 保留什么 | 放置位置 |
| --- | --- | --- |
| L0 不保留 | 可验收行为、代码可直接还原的结构/字段/调用链/DDL/命令、单次验证结果、已被推翻且不再约束当前实现的决定 | 归入 spec、代码、任务或 Git 历史；不进入长期 design |
| L1 一行结论 | 有明确取舍且一句话足以说明理由的决定 | 模块 design/decisions.md 表格 |
| L2 完整取舍 | 数据归属/真相源、跨系统边界、同步或迁移策略、失败/并发/幂等/一致性选择，或仍限制当前代码的被否决方案 | 主题 design 文档“关键取舍”，包含背景、决策、否决方案与原因、带来的约束、重新评估条件 |

L1 和 L2 记录选择与理由，不写实现说明。能由代码强制的约束优先加入代码、断言或测试；design 标明强制位置。无法在代码中强制的跨系统语义必须完整保留。

## OpenSpec 变更沉淀

1. 归档前确认 delta spec 已合并到模块主规格，并解决过期或冲突场景。
2. 从 design/proposal 中逐项归纳仍有效的设计决策，按 L0/L1/L2 判断；L1 写 decisions.md，L2 写主题设计。
3. 可重复操作移入 runbooks；一次性实施任务、旧方案和已过期附件不进入长期文档。
4. 每条 L1/L2 决策记录源 commit 和原始 design 路径，并用 git show 确认可追溯。
5. tasks 逐项核对实施与验证；未执行、未通过、接受风险或不适用需说明原因和后续闭环，不能把勾选等同验证通过。
6. 信息归位并通过链接与规格核查后，删除 change 过程包；共享 Git 历史是追溯来源，不保留第二套当前文档。

连续变更只记录当前有效的最终选择。已淘汰且不再约束实现的旧方案，不写入当前文档。
