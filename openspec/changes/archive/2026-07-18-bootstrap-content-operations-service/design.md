## 背景

游戏圈帖子管理需要将原平台的候选帖子转化为可运营的原创帖子池，并用 AI 提供分类、风险和回复建议。调研已验证：候选列表接口本身不能可靠地区分原创与转发；只有内容卡片详情中 `forward_topic_info` 缺失时，帖子才可视为原创。原平台接口属于已授权浏览器会话下的私有调用，其令牌、Cookie、请求模板和字段都可能变化。

本变更交付一个不建设独立前端、不区分角色权限的内部运营服务，要求人工审核全部 AI 结论，并为每个上游操作保留可追溯审计。部署规模为一个 Web 进程和一个后台 Worker，适合低运维成本的单体架构。

## 目标与非目标

**目标：**

- 建立可迁移、可测试的 Python 服务基础，承载采集、原创过滤、AI 评估、人工审核和日报。
- 使用 Django 模板运营工作台作为首期内部界面，避免单独维护 API 与前端应用。
- 以数据库中的持久化任务和检查点支持按北京时间日期窗口的断点采集与失败重试。
- 用明确的领域服务和适配器隔离原平台、OCR 与 LLM，避免业务逻辑耦合会话或供应商 SDK。
- 保证 AI 只生成建议和排序；所有原平台写操作必须在人工确认、重新验证原创状态后执行并审计。
- 以数据最小化、运行时密钥和结构化日志降低私有接口和个人信息风险。

**非目标：**

- 本变更不实现独立 SPA、移动端界面、多租户、权限体系或多游戏运营配置界面。
- 本变更不自动执行沉底、屏蔽、禁言、解除禁言、恢复、编辑、发布或评论回复等原平台写操作；每项已验证操作仍须人工二次确认和独立能力开关。
- 本变更不采集、存储或审核评论正文；只保留原创帖的评论计数作为互动指标。
- 本变更不提供编辑、发布、评论处置等未验证上游写接口；已接入的帖子状态与禁言操作仍可通过独立开关立即停用。
- 本变更不引入 Redis、Celery、消息队列或多实例并发运行。

## 技术决策

### 使用 Django 5.2 LTS 单体服务

服务采用 Python 3.12 和 Django 5.2 LTS，按 `posts`、`reviews`、`reporting`、`jobs` 等领域应用组织，业务规则放在服务层，外部调用放在适配器层。Django 自带 ORM、迁移、认证会话、管理后台和表单能力，能够以最少组件交付内部运营工具。备选的 FastAPI 需要自行补齐管理界面、ORM 管理、后台管理和表单工作流，不适合当前“无独立前端”的约束。

### 以 Django 模板运营工作台作为首期人工运营界面

首期以 Django Templates 与定制 CSS 提供“队列 + 详情”的原创帖子工作台：帖子无标题时以正文摘要识别，左侧筛选和队列不离开当前上下文，右侧呈现正文、投票文本、紧凑媒体缩略图、互动指标、当前状态与受控审核入口。图片和视频在页内模态框预览，可通过键盘在帖子及附件间切换。Django Admin 保留给账号与系统配置，不作为帖子编辑入口；不建立前后端分离的 API 契约或 SPA。

### SQLite WAL 与单 Web / 单 Worker 运行边界

数据存储使用 SQLite，启用 WAL、外键和合理的 busy timeout。SQLite 适用于首期的单点内部工具，迁移和备份成本低；其写锁限制意味着部署必须限制为一个 Web 实例和一个实际执行数据库写入的 Worker。按 Django ORM 和数据库迁移维护模式，未来可切换 PostgreSQL；不将 SQLite 特有 SQL 扩散到领域服务。备选的 PostgreSQL 能更早消除并发限制，但会增加当前部署运维成本。

### 以数据库任务表代替队列基础设施

`jobs` 应保存任务类型、参数摘要、状态、检查点、尝试次数、下次执行时间、错误摘要和幂等键。Django 管理命令分别承担 scheduler 和 worker：scheduler 创建每日采集、AI 评估、日报任务，worker 用原子认领处理任务并记录结果。此设计在进程中断后仍可恢复，且不依赖 Redis/Celery。每类任务必须幂等，采集任务以日期窗口和页码保存检查点；失败采取有限次数的指数退避，凭据失效或契约异常停止并转人工处理。

### 采用最小化的帖子数据模型与原创判定状态机

帖子以 `topic_id` 为业务唯一标识，保留 `content_id` 以查询内容卡片。候选记录首先进入 `CLASSIFICATION_PENDING`；只有成功读取 `getcontentcarddetail` 且 `forward_topic_info` 缺失时，才创建或更新 `ORIGINAL` 运营记录。字段存在且非空时标为 `FORWARD` 并立即丢弃转发链数据。缺少 `content_id`、接口错误或响应结构异常保留无敏感正文的异常记录，绝不默认归类为原创。正文、图片和视频媒体引用与互动快照使用最小投影；浏览数通过已单独验证的帖子详情适配器补齐，评论正文不进入模型。投票仅投影标题及按原始顺序排列的选项文本，作为和正文同等的审核内容；不保存投票/选项标识、用户投票状态或其他会话字段，以便识别藏头、拆字等隐性传播信息。

内容卡片的可读性不等价于帖子仍可运营。刷新原创帖时，先调用 `topicsearchgetdetail`；其已验证的业务错误码 `-10075007` 表示帖子已从原平台管理队列删除，即使内容卡片仍返回缓存也不得继续运营。原创帖子记录该状态和判定时间，在工作台、搜索和统计中保留并标明“原平台已删除”，且在状态恢复前拒绝任何上游处置。删除判定后仍可只读刷新内容卡片，以补齐历史正文、媒体和投票文本，但不得以此清除删除状态；仅当后续管理详情成功时清除该标记。

### 将上游、OCR 和 AI 定义为可替换适配器

领域服务只依赖协议化端口：`SourcePlatformClient` 提供候选列表、内容卡片、互动快照、状态读取和人工触发的写操作；`OcrClient` 提供图片文本及置信度；`AiReviewClient` 返回 Pydantic 校验的结构化评估。适配器负责 HTTP、会话上下文、超时、限速、错误映射与原始字段到内部 DTO 的转换。具体模型、OCR 厂商和浏览器会话注入方式由运行时配置选择，便于在接口变化时局部替换。

### 将人工确认作为不可绕过的上游写入门

AI 评估和策略命中只能创建或更新审核任务，包含建议动作、置信度、证据、策略版本和排序分数。任何上游写入服务都必须接受已保存的人工确认上下文，重新读取或判定目标仍是原创，并创建唯一 `operation_id` 与幂等键后才调用适配器。调用结束后保存请求摘要、前后状态、返回码、错误、执行者和时间。代码结构不得提供由 scheduler、worker 或 AI 服务直接调用写适配器的路径。

### 分阶段交付已验证的上游写适配器

沉底、屏蔽、禁言、解除禁言和恢复正常均已按操作独立接入。CDP 适配器只接受固定路径、固定动作和经验证的原因码/期限白名单，作者身份标识仅在禁言或解除禁言请求时从当前帖子读取并即时使用。工作台以状态 `2`（正常）、`4`（屏蔽）和 `8`（沉底）展示当前帖子状态，禁止提交重复的沉底或屏蔽，并提供相应的恢复正常转换。

每一次写入必须先读取目标状态，发送一次带确认令牌的人工确认请求，再读取状态验证预期结果。幂等键以帖子、动作和本次确认令牌组成：同一次确认的重复提交至多写入一次；运营人员在原平台恢复状态后重新打开确认界面，可以发起新的独立处置。请求超时、会话失效、响应结构变化、未知错误码或回读不一致时，审计记录为 `ACTION_FAILED`，不自动重试写入。每种操作由独立的能力开关控制，默认关闭；仅在对应的调研、测试和小范围人工验收完成后启用。Cookie、外层 token、插件 token、openid、完整跳转 URL 和请求正文均不得记录到调研文档、日志或业务数据库。

### 配置、隐私和可观测性

使用环境变量或部署密钥存储提供会话令牌、Cookie、模型密钥和其他敏感配置；它们不得进入数据库业务表、日志、导出文件、异常追踪或代码常量。使用 Pydantic Settings 校验运行时配置，`httpx` 设置连接/读取超时、限速和重试边界。采用 JSON 结构化日志，记录关联 ID、任务 ID、帖子 ID、适配器结果和可行动错误码，并对敏感字段做统一脱敏。质量工具采用 `uv`、Ruff 与 Pytest，外部调用在测试中使用 mock 或 fixture。

## 风险与权衡

- [私有接口随会话或页面版本变化] → 适配器集中处理请求模板和字段映射；将结构异常转为可见失败任务，禁止猜测新参数或继续写入。
- [SQLite 在并发写入下锁竞争] → 首期限制单 Web/单 Worker、使用 WAL 与短事务；监控锁等待和任务积压，超过边界时迁移 PostgreSQL。
- [AI 误判、提示词注入或证据不足] → 结构化 Schema 校验、保留证据、降低异常结果优先级，并要求每项处置人工确认。
- [帖子和作者数据包含个人信息] → 最小投影、默认不索引作者信息、不采集评论正文；禁言相关身份标识只在请求内存中使用，并在日志与报表中脱敏。
- [人工操作重复点击或上游超时] → 使用操作幂等键、操作前后状态读取、有限重试和失败队列，避免无限重放写请求。
- [复杂审核交互持续增长] → 首期采用队列 + 详情工作台与键盘导航；复杂表单与批量操作仍在同一 Django 项目内渐进扩展，不引入独立 SPA。

## 迁移计划

1. 初始化 Django 项目、依赖锁定、配置校验、SQLite 迁移和基础健康检查，在隔离环境用空数据库启动。
2. 部署单个 Web 进程与单个 scheduler/worker 进程，数据库文件放在持久化卷并纳入受控备份；写入启动时运行检查，拒绝多 Worker 配置。
3. 先以只读模式接入受控的原平台会话，对小日期窗口验证候选拉取、原创过滤、字段投影、断点续跑和日志脱敏。
4. 启用 AI/OCR 适配器和人工审核队列；以样本比对评估策略，确认所有建议都不触发上游写操作。
5. 对每个计划启用的写操作单独抓包验证参数、回读与幂等性，先在人工确认界面灰度开放，并保留停用开关。
6. 当需要多个并发 worker、多个 Web 实例、写锁告警持续出现或数据量超过运维边界时，按 Django 迁移流程迁往 PostgreSQL；回滚时停止 worker，恢复最近一次数据库备份，并保持上游写操作开关关闭。

## 待确认问题

- 首期的具体 AI/OCR 供应商、模型版本管理方式、知识库来源和成本预算待确定。
- 每日采集、日报生成的具体执行时间、失败告警渠道、数据保留期限和备份周期待运营方确认。
