## Context

系统已具备“生产者/业务页面入队 → `BackgroundJob` → 专用 Worker 消费”的执行模型，但系统配置台仍有两类入口归属问题：参数化历史补采按钮嵌在帖子采集 Worker 卡中；会话保活和永久禁言续期保留了与自动生产者等价的运行时 POST 路由。前者混淆业务任务与进程控制，后者使同一业务动作有多条入口，并造成主线规格互相矛盾。

本变更不改变队列、Job 类型、幂等键、范围冻结时机、Worker 消费范围或 Supervisor 控制协议。受影响使用者是系统配置台的已认证运营人员，以及可能调用两个旧内部 POST 路由的自动化调用方。

## Goals / Non-Goals

**Goals:**

- 建立清晰边界：自动生产者的人工运行只创建该生产者的业务 Job；参数化人工任务由对应业务区创建；Worker 卡只负责生命周期、日志和状态。
- 将历史补采并入“帖子采集”的“立即执行”弹窗，并保持当前操作游戏、1–744 小时、`MANUAL_INGEST_WINDOW` 与异步消费语义不变。
- 删除会话保活、永久禁言续期的重复旧路由，使自动生产者“立即执行”成为各自唯一人工入口。
- 以页面、路由、规格、文档和测试共同验证入口唯一性，且不在验证中启动 Worker 或访问上游。

**Non-Goals:**

- 不将所有业务 Job 都迁到自动生产者卡：依赖筛选条件、作者集合、报告参数或业务日期范围的任务继续保留在各自业务页面。
- 不修改 Job 数据模型、迁移历史任务、改变消费 Worker，或在入队时自动启动 Worker。
- 不修改自动规则、Scheduler 逻辑槽或会话服务的来源调用方式。

## Decisions

### 1. 以“业务语义”而非“消费者进程”决定 Job 创建入口

固定自动生产者的手动动作集中在“自动任务生产者”的“立即执行”入口；需要运营人员选择业务参数的动作放在独立业务区或对应业务页面。Worker 卡只保留启动、停止、重启、日志和运行状态。

选择此方案是因为 Job 的创建语义由生产者/业务参数决定，Worker 只是异步消费者；同时可避免“点击执行一次”被误解为同步调用 handler 或启动进程。

备选方案是在每张 Worker 卡保留“执行一次”，但仅入队。该方案虽不改变执行边界，仍会复制入口、扩大卡片职责并继续误导使用者，故不采用。

### 2. 历史补采作为帖子采集立即执行的受限模式

“帖子采集”的“立即执行”弹窗提供两种受限模式：默认的当前 30 分钟窗口创建 `MANUAL_CURRENT_INGEST_WINDOW`；历史补采模式仅接受 1–744 小时，始终以提交时当前操作游戏创建 `MANUAL_INGEST_WINDOW`。二者共用生产者入口和受认证、CSRF 保护路由，但保留各自 Job 类型、参数与消费者语义。

选择同一弹窗的模式切换，是因为它们都属于“帖子采集”的一次性业务工作，运营人员可在同一位置选择执行范围。历史模式不接受客户端 AppID，避免与生产者的当前范围冻结边界冲突；将其留在 Worker 卡或独立卡会继续分散入口。

帖子采集的立即执行弹窗复用系统配置弹窗的标准字段网格和 footer 结构，以保持输入尺寸、间距、提示和主按钮与“配置 AI 审核”等现有配置弹窗一致；仅替换展示结构，不改变表单字段、提交路由或服务端语义。

日指标的立即执行弹窗在手动日期输入前提供“昨天”“近 7 天”“近 30 天”快捷选择。预设按服务器上海日期生成，均以昨天为结束日期，确保不会选择可能尚未稳定的当日数据或未来日期；点击仅填充现有输入框，不自动提交或扩展 90 天范围校验。

周指标的立即执行弹窗使用相同的快捷选择交互，但预设为“上周”“近 4 周”“近 12 周”。周指标会将输入规范化为完整自然周，因此预设只提供已经完整结束的周：结束日为本周开始前的周日，开始日均为周一。这样不会因当前周尚未结束而将规范化范围扩展至未来日期；最长预设为 84 天，仍在既有 90 天上限内。点击同样仅填充现有输入框，不自动提交。

所有固定生产者的“立即执行”弹窗采用统一的操作块结构：共享弹窗标题和“仅创建后台任务”的说明；每个操作块有自己的执行范围标题、简要语义、参数区、Worker 等待边界提示和明确的提交按钮。无参数生产者也保留同样的说明和 footer，而不是只渲染孤立按钮。帖子采集的“最近 30 分钟采集”和“历史补采”使用两个独立表单：前者提交固定 `mode=current` 且没有可配置参数，后者提交固定 `mode=history` 和 1–744 小时参数。选择独立表单而非下拉框切换，是为了让每个按钮只对应一个 Job 类型和参数集合，避免隐藏/无效字段造成歧义。

### 3. 移除两个已重复的运行时 POST 路由

删除 `enqueue_session_keepalive_request`、`enqueue_permanent_mute_renewal_request` 及其 URL。会话保活与永久禁言续期统一通过 `run_scheduled_producer_now` 的白名单 producer key 创建 Job，继续由 `jobs.manual_producers.run_manual_producer` 复用领域入队函数。

选择删除而非 302/内部转发，是为了真正保持唯一入口，避免遗留调用方长期绕过生产者入口。该变更没有外部公开 API 的兼容承诺，但会在提案、规格和发布说明中标为 breaking；回滚只需恢复两条固定路由和视图，不涉及数据库迁移。

### 4. 用不触发 Worker 的最小验证覆盖边界

测试仅创建 Job 并断言 Job 类型、范围/参数、幂等复用、待执行语义和路由可用性/移除情况；页面测试断言历史补采表单不再属于 `service-ingestion` 卡，Worker 卡不含业务 Job 创建表单。不会启动 Supervisor、Worker、CDP 或上游写入。

## Risks / Trade-offs

- [旧内部调用方继续 POST 被移除路由] → 在变更中明确 breaking migration 为调用自动生产者立即执行路由；以 URL 解析测试确保旧路由不再悄然保留。
- [移动表单导致运营人员找不到历史补采] → 在“帖子采集”的“立即执行”弹窗中明确提供“历史补采（当前操作游戏）”模式，并在运维文档说明新位置。
- [误将历史补采并入固定生产者] → 规格和测试同时锁定两种 Job 的不同参数、任务类型和入口。
- [仅修改页面而遗留服务端重复能力] → 删除视图和 URL，并对 URL 解析及白名单生产者路由做回归测试。

## Migration Plan

1. 先更新 delta specs，确认历史补采和固定生产者人工运行的边界。
2. 将历史补采表单并入帖子采集生产者的立即执行弹窗，移除 Worker 卡和独立卡入口；历史模式复用生产者固定 POST 路由。
3. 删除历史补采及两条重复的运行时路由与视图，并把相关测试改为生产者立即执行路径。
4. 运行定向 Django 测试和 OpenSpec 严格校验；验证不启动 Worker、不创建逻辑槽且不调用上游。
5. 部署后，运营人员从自动任务生产者卡执行保活、续期和历史补采；旧 `POST /admin/runtime/ingestion/enqueue/` 的调用方改为 `POST /admin/scheduled-producers/post_ingestion/run/`，并提交 `mode=history` 与 `hours`，不得传入 `appid`。若必须回滚，恢复旧路由和视图以及原页面入口即可，既有 Job 无需迁移。
