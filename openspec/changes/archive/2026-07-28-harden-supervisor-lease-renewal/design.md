## Context

`RuntimeStore.write_json()` 先在目标目录写入完整临时文件，再以 `os.replace()` 原子发布。该模式避免读者看到半写入 JSON，但 Windows 上目标文件被短暂以不允许删除共享的方式打开时，替换会抛出 `PermissionError`。`instance-lease.json` 是高频写入、由多个 Web/Worker 守卫读取的文件；当前 `run_forever()` 未处理续租异常，异常会进入 `run_supervisor()` 的 `finally` 并停止全部受管服务。

租约是安全边界：只有实例标识匹配且未过期的服务才可继续处理新的工作。设计必须消除瞬时共享锁引起的级联停止，但不得把持续的运行态存储不可用误判为健康。

## Goals / Non-Goals

**Goals:**

- 保留完整 JSON 的原子发布语义，并在短暂共享锁冲突时有界恢复。
- 单次或短时续租失败不得停止 Supervisor 或受管服务。
- 持续无法发布租约时，仍由既有 TTL 使 Web/Worker 安全退出。
- 失败后不遗留无主临时文件，并提供不含敏感数据的诊断信息。

**Non-Goals:**

- 不改变租约 JSON 格式、30 秒 TTL、心跳协议、控制 API 或 Worker 命令。
- 不以直接覆写、软链接、版本化文件替代原子替换。
- 不实现 Windows Job Object、进程树托管或外部服务管理器；这些是独立架构变更。

## Decisions

### 1. 对原子替换做统一但严格限定的短暂故障重试

`RuntimeStore.write_json()` 保持“写完整临时文件后替换”的顺序。Windows 上仅对 `PermissionError` 且 `winerror` 为 `5`（实际观察到的 access denied）或 `32`（sharing violation）执行有界退避重试；`5` 也可能来自持久 ACL 故障，因此重试耗尽后必须抛出原始异常。其它平台不为该 Windows 共享锁类别引入新的重试规则。每次重试复用同一已经关闭且内容完整的临时文件。退避总时长必须小于 2 秒续租周期，建议使用带抖动的指数退避并设置不超过 1 秒的总截止时间。

其它错误、非可重试错误或重试耗尽仍向调用方抛出。失败路径必须尽力删除尚未发布的临时文件，且清理失败不得覆盖原始异常。

选择该方案是因为它保持读者只能看到完整旧值或完整新值，同时覆盖 Windows 文件共享锁通常持续时间很短的情况。直接覆盖会让 JSON 读者看到中间态；将重试仅放在租约写入会遗漏服务状态和心跳等同一原子写工具的同类故障。

### 2. 续租失败是主循环内的可恢复故障

`run_forever()` 必须在单轮续租发生 `OSError` 时记录脱敏诊断并跳过该轮 `reconcile()`，然后等待下一轮续租；不得让该异常逃逸至 `run_supervisor()` 的全局清理路径。跳过调和避免租约无法发布期间反复拉起会立刻因旧租约退出的子服务。

首次取得锁、发布初始实例租约或 bootstrap 期间的写入失败仍为启动失败：此时尚未建立可证明的当前实例，不应启动服务。

选择该方案是因为最后一次成功租约在 TTL 内仍是有效安全授权；持续失败超过 TTL 时，既有守卫会停止服务。继续运行 Supervisor 使其能够在文件系统恢复后重新发布同一实例租约并恢复调和，不需要不安全地延长 TTL。

### 3. 由 Supervisor 记录租约生命周期诊断

`RuntimeStore.write_json()` 只负责原子发布、清理未发布临时文件并保留原始异常，不负责记录日志；该工具也被服务状态和 Worker 心跳使用，在其中记录日志会缺少调用语境并可能被高频调用放大。

Supervisor 的租约循环在重试耗尽后必须输出服务名、操作类别、错误类别/系统错误码和尝试次数，不得输出租约内容、控制令牌、能力令牌或环境变量。为避免持久 ACL 或占用故障造成日志洪泛，同一段连续失败立即输出首条，之后按不少于 60 秒的间隔输出带累计失败次数的汇总；恢复后的首次成功续租应输出带累计失败次数的恢复事件，便于区分瞬时问题与长期存储故障。Worker 心跳继续使用既有连续失败阈值，不为本 change 新增逐次失败日志。

不新增数据库字段或控制 API；运行日志是本 change 的最小可观测面。

## Risks / Trade-offs

- [WinError 5 同时表示 ACL 问题] → `5` 与 `32` 均只做短暂有界重试；耗尽后保留原始异常，Supervisor 记录诊断，不吞掉 ACL、磁盘或目录故障。
- [持续失败时服务短暂保持运行] → 不改变 TTL；服务只能运行到最后一次成功租约的失效时间，之后既有守卫退出。
- [持续失败时反复重启子进程] → 失败轮跳过 `reconcile()`；仅在续租再次成功后恢复调和。
- [临时文件清理失败掩盖根因] → 清理为 best effort，原始替换异常优先保留；清理失败独立记录。
- [退避增加循环延迟] → 总等待严格小于续租周期，且仅发生在异常路径。
- [持续失败造成日志洪泛] → 首条失败立即可见，后续按 60 秒限频汇总，恢复时输出累计次数。

## Migration Plan

1. 在运行时原子写工具中加入重试与临时文件清理，并为可控时钟/睡眠编写单元测试。
2. 修改 Supervisor 主循环，将续租失败转换为可观测的本轮跳过，不改动 bootstrap 的失败语义。
3. 在 Windows 上执行锁竞争验证：人为持有目标文件的非删除共享读句柄，确认短暂持锁后同一实例继续续租且没有服务停止；持续持锁超过 TTL 时确认 Worker/Web 仍按既有安全路径退出。
4. 发布后观察 `runtime/supervisor/` 的遗留 `tmp*` 数量、续租失败日志和服务重启次数；若出现持续错误，按现有故障处置检查 ACL、磁盘与外部扫描程序。

回滚仅需回退代码版本；运行时租约格式与持久化服务状态不变，因此不需要数据迁移。回滚前应按既有流程优雅停止并重新启动 Supervisor。
