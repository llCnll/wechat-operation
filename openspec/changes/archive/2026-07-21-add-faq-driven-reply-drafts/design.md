## Context

系统当前由 `reviews.adapters` 将原创帖文本与 OCR 证据交给 AI 评估，并把合格输出中的 `reply_suggestion` 持久化为 `ReplyDraft`。草案当前只适用于 `FEEDBACK`、`SUGGESTION`，且提示词中没有已审核 FAQ 的受控内容；`knowledge_sources` 只是模型自由填写的列表。运营提供的《城主别慌张》游戏圈帖子回复 FAQ 参考工作簿包含 21 个常见场景，但工作簿本身不适合作为运行时依赖或不可追溯的自由提示词。

本变更扩大安全的本地草案覆盖面，并维持既有审核优先、人工维护和零发布能力。高风险内容、可能伤害第三方的举报，以及未经核验的事实性承诺必须优先受到限制。

## Goals / Non-Goals

**Goals:**

- 将经运营确认的 FAQ 转化为仓库内可审阅、可版本化、可测试的规则资料。
- 对 FAQ 命中的安全原创帖稳定地产生本地回复草案，并让运营人员看到场景和来源。
- 在模型输出、持久化和界面三个边界共同阻止高风险帖的公开回复草案。
- 对已存在草案保留历史语义，不将其静默伪造为 FAQ 命中结果。

**Non-Goals:**

- 不调用游戏圈评论/发帖接口，不自动或半自动发布草案。
- 不建设通用知识库、FAQ 后台编辑器、向量检索、活动规则抓取或模型微调。
- 不依据玩家举报对第三方账户作事实认定、禁言或其他自动处置。
- 不自动重跑全部历史帖子；需要新版 FAQ 草案的历史帖仍由运营人员显式重评。

## Decisions

### 1. 以受控 JSON 资料作为运行时来源，Excel 仅保留为原始参考

在 `reviews` 所属的受控资料目录维护单一 JSON FAQ 文件，包含资料版本、游戏 AppID、规则 ID、场景名称、适用关键词、回复要点、待补充信息、来源显示文本及禁止承诺事项。资料使用标准库可解析的 JSON，避免为了少量静态规则引入 YAML 依赖；原始 Excel 的文件名、工作表和行号记录在资料/文档的来源说明中。

选择 JSON 而不是在 Python 中硬编码模板，是为了让运营口径能被独立审阅、比较、版本化和测试；选择仓库资料而不是运行时直接读取 Excel，是为了避免端点文件缺失、格式变化或未经审阅的内容直接影响模型。

### 2. 让模型从服务端提供的候选规则中选择，并由服务端验证

服务端根据当前游戏和标题、正文、投票、图片 OCR 与可用视频证据中的文本关键词选出有限 FAQ 候选，将候选的场景名、要点、待补充信息、来源和禁止承诺传给模型。模型输出 `faq_rule_id` 或明确无匹配；服务端只接受候选集内的规则 ID，并从受控资料写入场景、来源和默认待补充信息。模型不得自行发明规则 ID、来源名称、客服路径或承诺。

相较于把完整工作簿直接附到系统提示词，该方式降低提示词长度和错误命中概率；相较于纯关键词模板，它保留模型对玩家自然语言和语气的理解。候选为空或模型未匹配时，系统可生成明确标识为“未命中 FAQ 规则”的通用安全草案，但不得写入资料来源、待补充信息、客服路径或无来源的事实性答复。

### 3. 将 FAQ 命中元数据持久化，并以评估输入版本触发显式重评

`ReplyDraft` 增加可空的 FAQ 规则 ID 和资料版本，现有 `knowledge_sources` 保留为展示来源。新字段在界面中展示为“回复场景”和“参考来源”。旧草案保持空的 FAQ 元数据并显示为历史草案，不推断其场景。

AI 提示词/评估输入版本纳入 FAQ 资料版本，使同一输入在规则变更后可被明确重评。为控制模型成本、避免意外改变既有审核结论，发布不会自动批量重新评估历史帖子；运营可使用已有的单帖重评入口。

### 4. 采用“先抑制、后生成、再持久化”的防御性边界

草案资格首先排除任何建议 `BLOCK`、`MUTE`、`BLOCK_AND_MUTE` 的帖子，并排除具有引流、私服、外挂、诈骗、色情、人身攻击等公开回复不安全风险标签的帖子，即使最终建议是 `HUMAN_REVIEW`。模型提示词必须要求相同结果；服务端在持久化前再次判断，避免模型或提示词失误绕过边界。

“疑似异常玩家”仅允许命中举证与客服引导规则，不得出现对被举报人是否作弊、处罚结果或处理时限的判断。所有草案仍为本地内容，不得触发上游写操作或新增后台发布作业。

### 5. 用受控的场景覆盖替代无限制的通用社区文案

首版资料覆盖运营工作簿中的 21 个编号场景及一条“疑似异常玩家”补充场景：问题处理、文案纠错、建议/吐槽、攻略与内容分享、社区讨论、活动相关问答及异常玩家反馈。社区互动类在无高风险信号时可生成草案：命中规则时使用受控口径；未命中时只能生成短、礼貌、非营销且无事实承诺的通用草案，并在工作台明确标识未命中。

这比对所有 `GUIDE`、`SOCIAL` 或 `QUESTION` 帖子无条件生成更可控，也让未来扩充场景时有明确审核入口。

### 6. 固定三种风格，单一可编辑草案为当前选择

每个 FAQ 命中的合格回复保留三条结构化候选正文，风格 ID 固定为 `WARM`（亲和互动）、`CONCISE`（简洁处理）和 `FORMAL`（正式稳妥）。三条正文必须共享同一 FAQ 场景、知识来源、待补充信息和安全限制，差异仅限语气、篇幅和互动方式。模型必须按固定 ID 返回全部三条；服务端验证集合完整、去重且每条非空，不能接受模型自造的风格或将同一正文重复冒充三种选择。

现有 `ReplyDraft.draft` 继续表示当前选择、复制和本地采纳的可编辑正文；新增 JSON 候选和当前风格 ID，以兼容既有编辑、复制和采纳流程。工作台切换风格时将对应候选带入现有编辑框；只有运营人员提交保存或采纳时才更新 `draft` 和当前风格。历史草案没有候选时显示为单一历史正文，不伪造三种风格。

选择结构化候选而不是将三段文字拼接进单一 `draft`，是为了让复制、编辑和本地采纳始终指向明确的一条正文，也避免运营人员误将三个版本同时发送。选择固定三种风格而不是任意数量，是为了稳定 Schema、测试和界面交互。

## Risks / Trade-offs

- [FAQ 资料过时或措辞包含未确认承诺] → 将资料版本化、审阅后入库；在规则中显式列出禁止承诺，测试拒绝修复时间、补偿、处罚和上线日期。
- [模型错误选择场景或捏造来源] → 只提供有限候选；服务端验证规则 ID，来源与默认信息从资料而非模型输出取得；未知 ID 不生成 FAQ 草案。
- [风险帖因建议动作为 `HUMAN_REVIEW` 而漏过抑制] → 同时按风险标签和建议动作实施资格检查，并加入回归测试。
- [扩展覆盖面增加低价值或重复互动] → 仅在显式场景命中时生成；运营可不采纳、编辑或删除本地草案。
- [新字段影响历史数据] → 采用可空迁移；旧草案不回填、不改变现有采纳记录。
- [模型遗漏或重复风格] → 服务端校验固定三风格 ID、非空和规范化文本去重；不合格输出不生成三风格草案。
- [FAQ 资料进入提示词被帖子内容注入影响] → FAQ 由服务端固定提供；帖子文本始终标记为不可信输入，模型不得执行其中指令或改写规则。

## Migration Plan

1. 将已审核 Excel 内容整理为受控 JSON FAQ 和运营说明，完成字段、禁止承诺及来源行号复核。
2. 新增 `ReplyDraft` FAQ 元数据迁移，保持新字段可空；部署前运行迁移和静态资源采集（若界面增加字段）。
3. 更新 AI 评估输入版本、提示词和持久化资格检查，部署后仅影响新入队或人工明确重评的帖子。
4. 先执行固定样本测试与单帖人工重评验证；确认工作台来源显示和“仅本地、未发布”提示后，再由运营开始采用新草案。
5. 如需回滚，停止使用新 FAQ 版本并回退应用代码；已生成草案仍是本地历史数据，不产生上游副作用。必要时可由运营删除或编辑草案，不回滚审核和处置记录。

## Open Questions

- FAQ 原始工作簿是否需要随仓库保留，还是只记录受控摘要、文件名、工作表和行号；默认不提交外部聊天目录中的原始文件。
- 运营是否需要后续为草案增加“删除/重新生成”入口；本变更保持现有编辑和本地采纳能力，不预设该交互。
