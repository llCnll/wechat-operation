## Context

当前 `OriginalPost` 没有作者关联字段。`topicsearchgetdetail` 已返回作者用户 ID、昵称、当前游戏 `block_info.block_end_time` 与 `global_block_end_time`，但同步逻辑仅保留帖子状态和互动指标。手动禁言先读取状态、再重复读取详情以取得用户 ID、写入、最后立即回读；既增加请求，也在上游状态延迟传播时产生假失败。

项目支持多个可管理游戏，当前游戏禁言是按 AppID 作用域的；全局禁言是独立字段。已有上游适配和操作审计禁止无限写入重试，所有原平台写入均需要人工确认和能力开关。

## Goals / Non-Goals

**Goals:**

- 将作者用户 ID 与原创帖关联，并以同一键查询历史帖子。
- 用独立表维护按游戏的当前作者禁言状态和最近昵称。
- 复用已有详情响应同步状态，避免日常采集增加额外上游请求。
- 在工作台展示状态并提供只读禁言管理列表。
- 在保持写前核验、写后回读和人工确认的前提下，消除仅为取得作者用户 ID的重复详情读取。

**Non-Goals:**

- 不采集评论、头像或作者资料页，不建立作者资料表。
- 不提供批量禁言、自动禁言、自动解除禁言或自动重试写操作。
- 不把首次发现时间当作上游真实禁言开始时间。
- 不将一次性回填变为常驻调度、批量处置或上游写入能力。

## Decisions

### 1. 原创帖直接保存 `author_openid`，不新增 Author 表

`OriginalPost` 新增可空、带索引的 `author_openid`。`AuthorMuteStatus` 使用同一用户 ID 连接状态与历史帖子。

选择该方案是因为作者当前仅需要帖子串联和禁言状态，不需要独立作者资料生命周期。相比 `Author` 表，它减少一层关联和迁移复杂度。代价是数据库不提供作者外键完整性；同步层须在每次成功详情读取时幂等写入相同用户 ID。

### 2. 禁言状态按 `(openid, source_appid)` 唯一

`AuthorMuteStatus` 使用本地自增主键，并以 `(openid, source_appid)` 唯一约束。字段包含昵称、当前游戏禁言截止、全局禁言截止、首次发现、最近同步和最近源帖子。

不能只以 `openid` 唯一：同一用户在不同游戏的当前游戏禁言可能不同，后一次同步会覆盖前一次本地禁言。全局禁言字段在每个游戏行中保留该游戏上下文下最近观测到的值，禁言管理始终以当前单一游戏过滤。

### 3. 使用管理详情作为唯一作者状态来源

在 `store_post_metrics` 或紧邻该函数的同步边界中，从同一详情载荷提取作者和禁言字段并执行状态 upsert。内容卡片、评论列表和额外作者接口均不参与。

`global_block_end_time=0`、缺失的 `block_info`、AppID 不匹配或过期时间均规范化为 `NULL`。每次成功详情同步都必须为具有作者用户 ID的帖子创建或更新状态观测行；无有效禁言以两个截止字段均为 `NULL` 表示。这样状态表可同时表达“已确认未禁言”和“状态未知”。已有状态行必须在每次成功同步中更新，即使状态不再有效。

每次详情请求在发送前记录 `source_requested_at`。状态 upsert 仅可使用请求起始时间不早于现有记录的载荷覆盖状态，避免较早发出的后台读取在较晚返回时覆盖人工处置后的验证结果。

### 4. 禁言管理为当前游戏的只读工作台 Tab

在既有内容管理导航中新增 Tab，并复用单选 AppID 上下文。列表仅查询当前有效本地或全局禁言，展示昵称、范围、到期、同步时间、最近帖子和历史帖子链接；昵称仅作为显示和筛选条件，用户 ID 为唯一关联键。

“本系统禁言时间”仅从成功的 `OperationAudit` 推导；无成功审计时显示“首次发现时间”。

### 5. 手动禁言复用作者关联但保留写前核验

每次人工禁言与解除禁言都先读取目标帖子详情，核验其仍为原创、未删除、处于可处置状态，并取得当前作者用户 ID与禁言状态。已同步的 `author_openid` 仅用于关联、展示和避免在写前核验之后再额外读取一次身份标识；核验返回的用户 ID必须与已保存值一致，否则拒绝写入并记录可处理错误。

写前核验确认作者已处于当前游戏有效禁言时，系统不得发送重复禁言写入。解除禁言仍须确认当前游戏有效禁言后才可写入。

写后验证固定使用同一详情接口最多 4 次：立即一次，之后在 2、5、10 秒后补读；总等待上限为 20 秒。首次回读未达到目标时允许上述受限补读，但绝不自动重复写请求。写接口响应失败、会话无效或超时均 SHALL 记录 `ACTION_FAILED`；即使回读已达到目标，也只能在审计中保存回读状态供人工核验，不能将该次失败响应标记为普通 `OK`。

### 6. 历史作者状态使用轻量的一次性 Job 回填

新增 `jobs/once/author_mute_status_backfill.py`，将该任务的定义和处理器明确归类为一次性 Job；不创建常驻调度器、独立 Worker 或复杂的批次协调模型。管理命令仅入队一个固定幂等键的 `AUTHOR_MUTE_STATUS_BACKFILL`，并由已有人工补采 Worker 串行消费。

任务以 `topic_id` 升序遍历全部 `OriginalPost`，在每一条完成后保存 `last_topic_id`、成功、跳过和失败计数。每条帖子最多读取一次既有管理详情，在请求前记录请求起始时间并只调用 `sync_author_mute_status`；不得调用 `store_post_metrics`，因而不得修改帖子正文、媒体、互动快照、审核状态或上游帖子状态，也不得创建 OCR、AI 或上游写操作。

历史空 `source_appid` 视为默认游戏 AppID；其他帖子使用其自身 AppID，按 AppID 缓存并最终关闭详情客户端。上游确认帖子已删除时计为跳过；单帖传输或契约异常计为失败并继续后续帖子，最多保留有限的脱敏失败样本。任务无自动失败重试；Worker 中断仍由通用 Worker 的既有恢复机制重新入队，并继续已保存的帖子游标。

## Risks / Trade-offs

- [用户 ID 在帖子中可能尚未补齐] → 工作台显示状态未知；每次手动处置均执行写前详情预检。
- [同一用户跨游戏本地状态不同] → 以用户 ID 和 AppID 联合唯一，列表强制单游戏上下文。
- [上游异步传播导致即时回读旧状态] → 固定 4 次、20 秒内的补读和明确的未确认失败状态，不重复写入。
- [并发详情读取乱序返回] → 以请求起始时间保护状态 upsert，且测试较早读取不得覆盖处置后的验证状态。
- [旧帖子没有用户 ID] → 正常同步渐进补齐；可由本变更提供的一次性回填任务补齐。任务按帖子保存简单检查点，Worker 中断后从该点继续。
- [昵称可变或同名] → 昵称只作最近展示与筛选，不能作为关联或唯一判断条件。
- [已同步作者关联与上游详情不一致] → 写前详情核验并拒绝写入，更新本地作者关联供后续人工核验。

## Migration Plan

1. 新增 `OriginalPost.author_openid` 与 `AuthorMuteStatus` 表、联合唯一约束及查询索引。
2. 部署同步逻辑，使后续采集、状态巡检、人工刷新和处置回读渐进补齐数据。
3. 部署工作台作者状态和禁言管理 Tab；缺失数据按“未知/未同步”展示。
4. 运营人员通过管理命令入队一次性历史作者状态回填任务，由既有人工补采 Worker 串行处理；任务仅保存简单的帖子游标检查点。
5. 回滚时先移除页面和写流程对新字段的依赖，保留表与数据；不得通过删除作者关联影响既有帖子和审计。
