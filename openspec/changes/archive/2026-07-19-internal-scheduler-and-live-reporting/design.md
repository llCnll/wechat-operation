## Context

当前自动采集由外部 `cron` 或 `launchd` 每 15 分钟运行 `run_scheduler --once`。该命令已能按时间桶幂等创建 `INGEST_WINDOW` 与 `STATUS_SYNC`，但部署还要维护外部触发器。现有 `reporting` 会把日报写入 `DailyReport`、`ReportMetric`，再由 CSV 命令导出；运营人员无法在工作台直接查看实时数据，互动指标还会错误地累加同一帖的所有历史快照。

系统首期使用 SQLite，已有一个 Web Server、一个采集 Worker、一个审核 Worker。CDP 仅能在采集 Worker 使用；AI 与上游写入均不得由调度器或日报查询触发。

## Goals / Non-Goals

**Goals:**

- 以项目内部常驻 Scheduler Worker 替代外部定时器，按固定时间桶稳定入队而不执行任务本身。
- 在工作台提供按北京时间日期范围和单选游戏查询的实时运营分析，覆盖现有日报的运营聚合指标。
- 让互动汇总每帖只使用最新快照，消除历史快照重复累加。
- 允许运营人员显式为选定范围入队互动刷新，并由采集 Worker 异步更新本地快照。
- 删除预生成日报、CSV 导出和其持久化表，降低维护与数据冗余。

**Non-Goals:**

- 不把定时循环嵌入 Django Web Server、请求处理线程、AppConfig 或页面访问路径。
- 不新增自动推送、文件导出、历史报表快照、趋势对比或报表下钻；范围互动刷新是唯一允许的人工触发异步任务。
- 不改变 15 分钟频率、30 分钟回看、固定游戏、手动历史补采、CDP、AI 或上游写操作边界。
- 不在 SQLite 上启动同类 Worker 的多个实例，也不实现多游戏自动调度。

## Decisions

### 1. 以独立 Scheduler Worker 作为内部调度能力

新增 `run_scheduler --loop`。它启动后立即检查当前北京时间时间桶，随后以短轮询间隔持续检查；符合条件时复用现有 `enqueue_scheduled_status_sync` 和 `enqueue_scheduled_ingestion` 入队。`--once` 可保留为诊断和测试入口，但生产运行方式改为 `--loop`，不再需要 cron 或 launchd。

不把循环放入 Web Server。Web 进程可能自动重载、水平扩容或被多个 WSGI/ASGI worker 复制，无法可靠表示单调度器生命周期；独立进程也能使用既有 Worker 的中断恢复、日志和进程管理方式。

同一时间桶的稳定幂等键仍是并发与重启下的最终保护。部署约束为一个 Scheduler Worker；即使误启动重复实例，同桶入队不会创建重复任务。Scheduler 只访问数据库任务表，不建立 CDP、AI 或上游写会话。

### 2. 复用既有任务与采集 Worker 边界

Scheduler 每个 15 分钟桶先创建 `STATUS_SYNC`（上限 20），再创建固定 AppID 的 `INGEST_WINDOW`（30 分钟回看、页大小 20）。采集 Worker 继续是唯一消费者，审核 Worker 继续只消费 `OCR_EXTRACT`、`AI_EVALUATE`；不增加新的任务类型或第四个业务 Worker。

运行中断超过 30 分钟仍可能形成采集空洞，沿用 `enqueue_ingestion` 人工补采。选择不增加补偿扫描，避免在本次改变运行方式时扩大采集策略范围。

### 3. 将日报聚合改为无副作用的范围分析服务

将入口命名为“运营分析”，用 `build_live_operations_analysis(start_day, end_day, appid)` 替代 `generate_daily_report`。该查询服务返回内存中的结构化摘要，不写入模型、不创建 Job、不缓存 CSV。页面以北京时间含首尾的日期范围和单选游戏调用它；默认最近 7 天（含当天），范围最长 31 天，并渲染摘要卡与分类、风险、人工最终处置分布。

帖子范围保持当前日报业务含义：候选/转发/待判定以候选创建时间计入所选北京时间日期范围；原创帖及其审核、分类、风险、互动、最终动作以原创帖发布时间计入。不存在任何报告完整性快照；页面展示的是查询时数据库中的当前状态。

### 4. 互动指标按每帖最新快照聚合

实时服务对所选范围内每个原创帖使用 `InteractionSnapshot` 按 `captured_at`（同一时间再按主键）倒序的最新记录，再汇总浏览、点赞、回复、分享。空快照字段按零处理。这样同一帖子被刷新或状态巡检多次时不会重复计量。

### 5. 由采集 Worker 异步刷新范围互动指标

运营人员在“运营分析”页提交有效范围后，系统创建 `METRICS_REFRESH_WINDOW` 任务并立即返回页面；该任务由既有采集 Worker 消费，而不是由 Web 请求、Scheduler 或审核 Worker 建立 CDP 会话。范围以当前游戏的 `OriginalPost.publish_time` 确定：只选择北京时间范围内的原创帖，`CandidatePost` 中的 `FORWARD` 和待判定候选永不参与。任务以选中原创帖的 `topic_id` 稳定升序保存检查点；`topic_id` 只用于排序与中断恢复，不决定业务范围。Worker 逐帖调用只读详情接口并仅写入浏览、点赞、评论、分享的 `InteractionSnapshot`。已删除或不可读取的帖子会记入任务检查点并继续下一帖；其他可重试的契约或传输异常沿用任务重试机制。任务不得刷新正文、媒体、投票、AI 评估、审核状态或调用上游写操作。

相同范围正在排队或执行时，页面复用该任务以避免重复 CDP 回读；任务结束后运营人员可以再次请求同一范围刷新。页面展示最近一次范围刷新任务的状态、已处理数和跳过数。

### 6. 删除预生成报表存储和导出

删除 `DailyReport`、`ReportMetric`、生成与导出管理命令、相关任务/测试以及 CSV 文档。添加 Django 迁移删除两张表；按用户确认不迁移或保留历史预生成数据。保留 `reporting` Django app，承载实时查询服务、视图、模板与测试。

### 7. 在审核详情按需提供本地回复建议

`ReplyDraft` 已是一帖一条的本地记录，继续仅由合格的反馈/建议 AI 评估创建或更新。内容管理队列只为有草案的帖子显示低干扰提示；不在列表中展开草案正文，避免影响审核扫描效率。

选中帖子后，审核详情在 AI 风险依据之后、人工处置之前显示可折叠的“回复建议”卡片。卡片展示诉求摘要、可编辑回复正文、待补充信息、已验证知识来源、风险提示与本地采纳状态。保存只更新本地 `ReplyDraft`；复制只使用浏览器剪贴板；“标记已采纳”只记录运营人员已采用该本地建议，不能表示或触发已回复用户。

没有草案时不显示空卡片，也不创建草案。原有风险策略继续抑制屏蔽或禁言建议帖的草案生成。此功能不新增 Worker、任务类型、CDP 会话或上游适配器，更不提供原平台评论/发布调用。

## Risks / Trade-offs

- [Scheduler 进程未启动或停止超过 30 分钟] → 健康与运行手册明确要求常驻；运营人员使用现有手工补采命令补洞。
- [误启动多个 Scheduler Worker] → 同时间桶任务键幂等，且运行文档限制为单实例；不在 Web 进程内运行可减少此风险。
- [实时聚合或回读范围过大] → 限制为单游戏、最多 31 个北京时间自然日；查询使用每帖最新快照子查询，刷新使用检查点逐帖执行，后续规模增长再设计索引或缓存，不恢复日报快照表。
- [删除日报表丢失历史快照] → 变更前备份 SQLite；本次明确接受不保留历史报表数据。
- [实时指标与旧导出结果不完全一致] → 新口径有意修复历史快照重复累加，并在页面与文档说明最新快照口径。
- [运营人员误解“采纳”为已回复] → 卡片固定标注“仅本地记录，未发布到原平台”，按钮使用“标记本地已采纳”而非“发送”或“回复”。

## Migration Plan

1. 部署代码和迁移前备份 `var/operations.sqlite3`。
2. 停止外部 cron/launchd 调用，并启动单个 `run_scheduler --loop`、采集 Worker 与审核 Worker。
3. 应用迁移删除预生成日报表；移除生成/导出命令和相关文档入口。
4. 在工作台查询默认近 7 天和指定游戏范围，核对候选、原创、审核和互动指标；互动量以每帖最新快照为准。
5. 对一个小范围提交互动刷新，确认采集 Worker 完成任务后重新查询范围，核对最新互动快照。
6. 若需回滚，在停止 Scheduler Worker 后恢复代码、数据库备份和外部定时器；已删除日报快照仅能从备份恢复。

## Open Questions

无。运营分析默认最近 7 天（含当天）、默认游戏为城主别慌张，单次范围最大 31 天；不保留 CSV 与报表历史，均已确认。
