## Context

当前 `/admin/` 的“初始化与运行状态”同时承担首次恢复指引、服务健康、配置入口和可选能力开关。节点按实现模块排列，而不是按运营人员完成工作的依赖排列：受控 Chrome、游戏圈会话服务和外层会话重复出现；当前操作游戏既是来源任务的业务范围，又被混入会话链路；Scheduler 与 Worker 的进程状态又与调度规则和 AI/OCR 配置混排。

这会产生两个问题。其一，页面的“核心审核能力已就绪”可能在未选择当前操作游戏或 Frame 未就绪时成立，和来源任务的真实可执行性不一致。其二，同一恢复操作在多个节点出现，运营人员无法区分应先恢复会话、选择范围，还是重启服务。

本 change 重编排运行控制台的状态投影与入口归属，并补齐运行态中 Frame 与当前范围的可验证绑定。Supervisor、游戏圈会话、任务队列及固定控制通道的行为和所有权保持不变。

## Goals / Non-Goals

**Goals:**

- 从一份服务端脱敏运行快照派生“按运行流程”和“按服务管理”两种视图，防止各自计算就绪状态。
- 使流程视图能够按固定依赖顺序给出唯一、可执行的下一步，最终确认基础来源和核心审核服务均可运行。
- 使服务视图能够回答每个服务的用途、前置条件、当前缺失项、固定控制动作、日志和关联配置入口。
- 保留当前操作游戏为全局业务范围；明确区分外层会话有效与当前游戏 Frame 有效。
- 将可选能力从基础流程中剥离，但保留其服务状态、配置和高风险边界。

**Non-Goals:**

- 不改变 Supervisor 服务注册、默认期望状态、进程所有权或生命周期协议。
- 不新增、删除或改变来源 Job、Worker consumer、游戏圈 IPC、CDP 命令、登录行为、任务重试或上游写入。
- 不增加用户可编辑的服务依赖、任意命令、任意 URL、token、Cookie、target ID 或来源响应展示。
- 不将自动任务生产者规则管理并回运行控制台；该区域继续独立管理调度计划。

## Decisions

### 1. 使用单一运行快照，再派生两种投影

服务端 SHALL 先收集一个 `RuntimeConsoleSnapshot`：Supervisor 可达性与 Web 健康、固定服务状态、当前操作游戏、受控会话投影、与范围绑定的 Frame 投影、审核配置与策略状态、可选能力状态。快照只包含固定服务键、中文展示名、布尔/枚举状态、脱敏原因、检查时间和固定动作标识；范围绑定只使用本地单调 `scope_version`，不在状态、日志或错误中暴露 AppID。

随后在同一请求内派生：

- `flow`: 有序运行节点、每一步完成条件、当前阻塞原因和唯一恢复动作；
- `services`: 按基础托管、游戏圈访问、调度与业务 Worker、可选能力分组的服务卡；
- `readiness`: 控制台可用、来源可用、核心审核可用和可选能力摘要。

快照本身不持久化，也不在模板或 JavaScript 中重新计算依赖。选择这一方案是为了避免当前 `pipeline_ready`、顶栏会话状态和服务卡使用不同口径。替代方案是为两个页面分别构建 context；其初期改动较小，但会再次出现状态漂移，故不采用。

### 2. 将 Frame 运行态绑定到当前范围版本

`GameCircleLoginRuntimeState` SHALL 新增可空的 `frame_scope_version`。会话服务仅在某个 scope 的 lease 经最小只读验证后将其设为该 scope 的版本并投影 `READY`；任一未就绪、建立中、浏览器不可用、登录待确认、范围切换或旧 lease 结果不属于当前 scope 时都 SHALL 清空它。控制台仅当 `frame_state=READY`、`frame_scope_version` 等于当前 `ActiveGameScope.scope_version`、会话投影未过期且 Chrome 与会话服务均运行时，才将当前游戏 Frame 和来源能力投影为有效。

该字段是本地范围版本而非来源身份或认证材料，且不需要保存或显示 AppID。它解决范围切换与冻结 scope 保活并发时，旧 scope 完成后把全局 `READY` 误用于新范围的问题。替代方案是通过 Web 向会话服务新增一次按 AppID 查询的 IPC；这会扩大控制面并在页面刷新时增加 IPC 依赖，故不采用。

### 3. 流程视图按运营依赖而非进程模块排序

默认流程固定为：

1. 控制台与 Supervisor 可用；
2. 受控游戏圈连接（受控 Chrome 运行、会话服务运行、外层会话有效）；
3. 当前操作游戏（目录可刷新、范围已选择）；
4. 当前游戏 Frame（当前 scope 存在经最小只读验证的 ACTIVE lease）；
5. 审核能力配置（AI 配置完整、唯一启用策略含规则）；
6. 核心后台服务（Scheduler、实时采集、人工补采、AI 审核 Worker）。

指标快照服务显示在服务视图的业务 Worker 组中，但不阻塞“核心审核可用”；永久禁言维护、OCR、视频审核、人工处置授权和 AI 自动处置均为可选能力。该顺序表达“运营控制台能否完成来源读取和审核”，而不是 Supervisor 启动子进程的内部顺序。

每个未完成流程节点只显示一个动作：会话节点按状态提供安全的会话恢复动作；范围节点提供目录同步或范围选择；Frame 节点提供建立当前游戏 Frame；配置节点打开对应配置；后台服务节点跳转至对应服务卡。跳转至服务卡时，页面 SHALL 先切换至“按服务管理”视图，再定位目标服务组。流程不得显示服务停止、日志或重复的保活入口。

### 4. 服务视图按受管职责分组，避免把业务范围误作服务

服务视图使用以下分组：

- 基础托管：Web 与 Supervisor 只读健康；Web 仅显示既有重启控制。
- 游戏圈访问：受控 Chrome 与游戏圈会话服务作为一个依赖组展示，列出 Chrome、外层会话与 Frame 三层状态；人工控制会话服务而非提供独立的受控 Chrome 生命周期入口。
- 调度与业务 Worker：自动调度器、帖子采集（实时采集与人工补采子服务）、指标快照、AI 审核和禁言维护。
- 可选能力：OCR、视频审核、人工处置授权与 AI 自动处置。

当前操作游戏显示为两个视图共用的“工作范围”栏，包含当前值、范围说明和唯一更换入口；它不属于任何服务卡。这样既保留服务级诊断，又不使“切换游戏”与会话维护的生命周期混淆。

替代方案是将当前操作游戏放入游戏圈会话服务卡。该方案会让用户误以为切换游戏等于重启或配置服务，且与采集、指标、人工操作的范围语义冲突，故不采用。

### 5. 明确就绪等级、会话新鲜度和入口归属

`控制台可用` 只表示 Supervisor 控制通道可达且 Web 健康；`来源可用` 还要求 Chrome、会话服务、外层会话、当前操作游戏与当前范围绑定的 Frame 均有效；`核心审核可用` 在来源可用基础上要求 AI 配置、启用策略、Scheduler、实时采集、人工补采与 AI 审核 Worker 可用。

外层与 Frame 投影仅在其 `checked_at` 未超过现有十分钟有效期、Chrome 与会话服务均运行时可被使用；超时或任一服务未运行时统一视为未知或未就绪。顶部只显示当前等级和第一个阻塞步骤。外层会话有效绝不能投影为 Frame 有效。可选能力的未配置或停止不得降低来源可用或核心审核可用。

同一可变操作只保留一个主入口：登录页/会话检查归游戏圈连接；目录同步与范围切换归工作范围；建立 Frame 与手动保活归游戏圈会话服务；服务生命周期和日志归服务视图；调度规则归自动任务生产者。流程视图可链接到该入口，但不得复制表单或 POST 操作。

### 6. 区分进程生命周期与业务可处理条件

服务卡 SHALL 分别展示：

- `生命周期状态`：Supervisor 是否实际运行或期望运行该固定服务；它决定启动、停止、重启和日志入口。
- `业务可处理条件`：服务在当前配置下能否产生或处理其业务工作；条件缺失时服务仍可运行并等待或按既有 Job 语义处理，页面不得把它表述为“无法启动”。
- `缺失后的行为`：固定为“等待后续任务”“任务延后/失败并保留既有摘要”或“需要配置/授权”，并提供唯一配置或诊断入口。

映射 SHALL 固定：Scheduler 的业务条件是至少存在启用规则，但无规则时仍保持运行；实时采集、人工补采和指标快照依赖当前范围与 Frame 才能完成来源工作，但 Worker 可继续运行；AI 审核依赖 AI 配置与启用策略才可完成评估，但 Worker 可继续运行；禁言维护的写入授权是具体续期 Job 的条件，不得阻止该 Worker 消费只读状态刷新 Job。视频审核和 AI 自动处置继续按各自可选启用条件表达。

替代方案是以一个“服务可用”布尔值同时表达进程、配置和任务条件。它会将空规则、暂时无 Frame 或未配置 AI 误报为启动失败，增加排障歧义，故不采用。

### 7. 采用服务端渲染的可访问切换，不引入前端状态依赖

双视图使用语义化 tab 与受控面板，默认展示流程视图；用户切换不改变任何运行状态。浏览器 MAY 将用户最后选择的视图保存在本地偏好中，使固定 POST 操作重定向回页面后仍回到同一视图；服务视图内的固定控制表单 MAY 在本次提交前保存一次性滚动位置，并在重定向返回后恢复。两类浏览器偏好不得传给服务端、不得参与就绪计算或影响任何控制行为。服务端仍完整渲染两类脱敏数据，前端仅负责显示面板和焦点管理。这样不引入新的 API 或前端构建链，也保证禁用 JavaScript 时至少能读取状态与访问固定表单。

## Risks / Trade-offs

- [两个视图表达相同状态但文案不同] → 使用单一快照和固定就绪等级；为快照投影和模板结构编写测试，禁止模板内二次判断依赖。
- [会话状态过度简化，掩盖 Chrome、外层会话、Frame 范围或新鲜度差异] → 在游戏圈访问组中始终分层显示三项状态；Frame 必须匹配当前 `scope_version` 且未过期，流程节点仅汇总当前阻塞原因。
- [收敛入口后用户找不到低频动作] → 服务卡保留日志、重启、启动/停止和可选维护折叠区；流程在对应阻塞时深链到服务卡。
- [服务控制台改动误扩大为进程生命周期改造] → 不变更服务注册、Supervisor 控制协议或 CDP；测试固定服务/操作白名单和受控 Chrome 仅经会话服务恢复的边界。
- [状态轮询期间出现短暂不一致] → 快照在单次请求中采集并携带统一检查时间；短暂未知状态显示“检测中/暂不可用”，不得推断为有效。

## Migration Plan

1. 先实现快照与双视图投影，在测试中固定新的就绪等级、依赖顺序、服务分组和入口唯一性。
2. 用新模板和样式替换单一 Pipeline；保留既有 POST 路由、CSRF 表单和 Supervisor 代理，不改变 URL 契约。
3. 更新系统总览与运行手册，使首次恢复路径和服务排障路径分别对应两个视图。
4. 发布时先应用新增运行态字段的数据库迁移，再按既有会话发布约束重启 Supervisor；Supervisor 将替换受控 Chrome 与游戏圈会话服务，随后重新采集静态资源并确认 Web 健康。不清理队列，不复制会话状态，也不重放任务或人工写入。

回滚时保留新增的可空范围版本字段，仅还原 Web 模板、样式、context 投影和会话服务对该字段的写入；运行配置、后台任务、会话 lease 和 Chrome profile 均不需要迁移或重放。

## Open Questions

- 无。服务组与可选能力的边界依据现有 Supervisor 注册表和既有运行手册确定；如未来新增 Worker，只需在单一快照的服务元数据中声明其组别、前置条件和是否影响核心审核可用。

## Visual System Extension

本次视觉重构以“精密运行台”而非通用 Admin 面板为方向：清晰的状态光谱、具有节奏的排版与可扫读的操作层级，强调当前阻塞步骤与可操作性。视觉完成度以顶级数字产品为目标，但 SHALL 以克制、可读、可预测的运维体验实现：不增加装饰性首屏、不重排既有信息层级、不使用会干扰服务控制的实验性交互。原有浅色运营配色 SHALL 保持为默认外观；深色外观仅作为用户主动选择的本地偏好。

所有图标 SHALL 使用本地随仓库交付的 Lucide SVG 图标集；系统配置页面不得使用 Emoji、Unicode 图形符号或字体图标替代状态、导航与操作图标。图标须带可访问文字或 `aria-hidden`，不得承载唯一语义。

视觉改造 SHALL 保持服务端渲染、无 JavaScript 降级、现有 CSRF 表单和固定 POST 路由。动效仅用于状态变化、视图切换和焦点反馈，遵守 `prefers-reduced-motion`，不得自动触发请求、Job、CDP 或上游操作。页面在窄屏下须退化为单列，保持首个阻塞动作、服务状态和高风险操作可读且可点击。

### Visual Decisions

- 运行概览使用一张主舞台：以核心可用性、检查时间和首个阻塞行动为视觉锚点；流程与服务是同一舞台上的可切换视图。
- 工作范围独立为“任务上下文”，不混入服务卡；范围切换保持受控表单，但采用渐进披露，避免占据首屏。
- 服务卡采用固定信息序列：状态、用途、生命周期、业务条件、缺失行为和控制。可选能力保持低权重，危险写入授权使用明确风险色与文案。
- 同一视觉 token SHALL 覆盖运行概览以下的自动任务、核心配置、规则明细、运行健康、数据追溯与所有配置/日志对话框；主题切换不得只改变首屏而使下方内容回退到另一套配色。
- 自动任务、核心配置、运行健康与数据追溯 SHALL 与运行概览采用一致的双层层级：区域标题位于外层面板内，具体卡片与规则明细位于其内层内容面板；不得让标题与内容在视觉上脱离。
- 色彩、间距、边框、阴影和动效统一为 CSS token；不增加前端依赖、远程字体、远程脚本或运行时 CDN。
- 主题切换 SHALL 只改变视觉 token，不改变 DOM 数据、服务控制、可访问名称、路由或表单提交；默认浅色，深色偏好仅保存于当前浏览器的本地存储。切换控件位于系统配置导航栏，使用带可访问文字的 Lucide 太阳/月亮图标开关，不在页面内容区重复占用操作空间。
- 操作反馈 SHALL 是固定尺寸的独立组件；图标必须显式受限于反馈项，不得依赖浏览器 SVG 默认尺寸或继承页面布局。成功、警告和错误仅改变状态色与图标，不改变反馈位置、内容层级或关闭行为。
- 纯 CSS 的显隐切换仍可工作；浏览器不支持高级选择器时两个视图均保持可读。
