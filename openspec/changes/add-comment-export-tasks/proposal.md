## Why

一次性脚本已经证明受控 Frame 可以分页读取指定帖子的顶层评论，但它没有运营页面、任务状态或可追溯结果。运营人员需要先确认帖子，再设置规则并异步执行；完成后的命中评论必须作为任务结果保存在数据库中，能够从任务列表查看并导出，而不是再次请求平台。

## What Changes

- 新增流程式“评论导出”工作区：确认帖子 ID、配置规则、创建任务三个连续步骤；每步必须完成校验才可进入下一步。
- 新增评论导出 Run 与命中结果行。Worker 只持久化命中评论的导出字段；不命中的评论、完整上游响应、认证材料均不得落库。
- 任务创建成功后显示明确成功反馈与“前往任务列表”入口；任务列表提供进度、失败分类、命中结果查看及从数据库结果生成 CSV 的入口。
- 由人工补采 Worker 通过固定只读 IPC 按每页 100 条读取顶层评论，按冻结规则写入数据库结果；CSV 导出不得重新调用平台。
- 任务创建时重新验证已确认帖子并冻结当前游戏范围、帖子/作者快照、规则版本和规则值；同一创建者的活动重复提交复用同一任务。
- 删除一次性脚本作为正式能力入口，避免脚本读取 Supervisor capability；评论分页来源契约仅供受管 Worker 使用。

## Capabilities

### New Capabilities

- `comment-export-workflow`: 从帖子确认、规则冻结、后台执行、数据库结果追溯到 CSV 导出的完整评论导出工作流。

### Modified Capabilities

- `internal-job-scheduling`: 为 `COMMENT_EXPORT_V1` 定义手动一次性任务的幂等、恢复和人工补采 Worker 消费边界。

## Impact

- 受影响代码：`posts` 的评论导出工作区、模型、结果列表与导出视图；`jobs` 的任务类型和人工补采 handler；固定评论分页来源适配器。
- 数据库：新增 Run 和命中结果行；结果行保存 `reply_id`、评论者 OpenID、昵称、创建时间、正文和提取数字，并关联冻结 Run。
- 服务：人工补采 Worker 新增一个只读任务类型；不新增 Scheduler 任务、常驻服务、外部队列或文件产物存储。
- 数据：命中结果作为受权限保护的运营任务数据保存在数据库，默认不自动清理；不命中的评论和上游原始载荷不保存。
