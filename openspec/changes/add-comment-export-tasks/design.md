## Context

现有固定 `POSTS_LIST_TOPIC_REPLIES` 已验证：`cur_page` 是零基页码，平台稳定接受每页 100 条，`next_offset` 不能回填为页码。一次性脚本完成过单帖导出，但直接读取运行态 capability、将结果写文件且没有任务生命周期，不能演变为页面功能。

用户的新目标是结果数据化：运营人员不在完成时立即下载临时文件，而是在任务列表中查看持久化的命中结果，并按需从本地数据库导出。命中行仍包含正文、昵称与 OpenID，因此必须限制为创建者、当前游戏范围和已认证会话可访问。

## Goals / Non-Goals

**Goals:**

- 提供清晰的三步页面：确认帖子 → 配置规则 → 创建任务成功。
- 将完成任务的命中结果保存为可追溯数据库记录，支持任务列表查看与无需来源调用的 CSV 导出。
- 只在受管人工补采 Worker 中读取评论；页面不读取评论分页，不处理 capability 或 token。
- 对同一创建者的重复活动提交去重，且在重试后保持结果计数和结果行准确。

**Non-Goals:**

- 不保存不命中的评论、子回复、图片、头像、点赞、完整来源响应或认证材料。
- 不开放任意正则、任意脚本、任意 AppID/作者 OpenID/页大小输入，或跨帖批量导出。
- 不生成长期运行态 CSV 文件、每日清理 Job、自动评论任务或平台写操作。
- V1 不提供任务取消、跨用户共享结果或结果自动保留期限配置；结果作为运营任务记录长期保存，后续数据治理变更须单独设计。

## Decisions

### 1. 用三步流程承载确认与创建

评论导出工作区使用可见步骤条和单一当前步骤，不将全部表单同时展开：

1. **确认帖子**：输入正整数帖子 ID，调用既有固定帖子详情读取，展示标题、正文摘要、阅读/点赞/评论指标和作者昵称；页面不显示作者 OpenID。
2. **配置规则**：确认成功才显示关键词输入和固定的“提取第一段连续数字”规则说明。
3. **创建任务**：提交时携带只含帖子 ID、活动范围版本和帖子内容指纹的短时确认凭据；服务端重新读取帖子详情，验证 AppID、作者 OpenID 与内容指纹未变后创建 Run 与 Job。成功后显示 Run 编号、初始状态和“前往任务列表”。

确认凭据不得包含 OpenID、正文、token 或来源响应。创建时重新确认来源比让浏览器回传作者 OpenID 更安全；若帖子已变化或确认超时，服务端拒绝创建并要求重新执行第一步。

### 2. 规则为版本化的受限结构

V1 采用 `keyword-first-digit-v1`：一个去首尾空白、1--100 字符的关键词；评论必须包含关键词和至少一段 ASCII 连续数字；导出第一段连续数字。来源 Unix 秒时间用 `Asia/Shanghai` 格式化为 `YYYY-MM-DD HH:mm:ss`。

规则版本、关键词和时区在 Run 中冻结。页面不允许输入正则或提取代码；若将来需要最长数字串、多个关键词或其它解析器，应创建新规则版本，不修改 V1 语义。

### 3. Run、Job 与结果行分层保存

新增 `CommentExportRun` 一对一关联 `BackgroundJob`，保存来源 AppID、帖子 ID、标题快照、作者 OpenID/昵称快照、规则、创建者、进度和结果就绪时间。新增 `CommentExportResult`，保存 `run`、`reply_id`、评论者 OpenID、昵称、创建时间、正文和提取数字；数据库唯一约束为 `(run, reply_id)`。

Run 是任务与权限边界，Result 是唯一导出数据源。通用 `BackgroundJob.parameter_summary` 仅保存 Run ID 和执行范围版本，不保存关键词、作者 OpenID、正文或结果路径；结果列表与导出仅允许 Run 创建者在相同活动游戏范围访问。V1 不共享他人 Run；活动去重键必须包含 `created_by`。

选择结果行落库而不是最终 CSV 文件，是为了支持任务列表可查看、按需多次导出和避免文件保留/清理与数据库状态分叉。代价是持久化了命中评论；该范围通过只保存命中行、创建者隔离和后续独立数据治理能力控制。

### 4. Worker 每次尝试从零构建未发布结果集

`COMMENT_EXPORT_V1` 只由人工补采 Worker 认领。Handler 使用冻结范围和作者 OpenID，固定调用 `POSTS_LIST_TOPIC_REPLIES(topic_id, topic_openid, page, limit=100)`，只读取顶层评论；下一页为 `page + 1`，不使用 `next_offset` 作为输入。

每个 Worker 执行尝试开始时，在事务中删除该 Run 尚未发布的旧结果行并将 Run 进度与 Job checkpoint 重置为零；随后逐页按 `reply_id` 去重、匹配 V1 规则并批量写入 Result，按页更新进度。只有读到末页且所有结果行写入成功，才设置 `results_ready_at` 并让通用 Worker 标记 Job 成功。中断或可重试失败后遗留的部分 Result 永不在页面显示；下一次尝试先清空后重建。

这比续写半成品更简单，也避免动态页重叠、旧 checkpoint 和结果计数累加造成错误。代价是失败重试会重新读取该帖，但任务为单帖、每页固定 100 且同创建者活动任务去重，可接受。

### 5. 任务列表为唯一的结果查看和导出入口

创建成功后的页面只给出“前往任务列表”链接。任务列表默认仅显示当前用户、当前活动游戏范围内的 Run，展示帖子、关键词、Job 状态、处理进度、命中数、创建/完成时间和固定失败摘要；未成功或未就绪的 Run 不显示结果行或导出按钮。

结果详情按 Run 分页显示已保存的命中行。CSV 下载端点从 `CommentExportResult` 按稳定顺序流式写出 `utf-8-sig`，字段严格为 `openid`、`nick_name`、`create_time`、`content`、`game_id`；不得读取平台、创建 Job 或保存文件。

### 6. 保持受控会话单向能力边界

Web 的确认读取可通过既有固定帖子详情 IPC 进行，但创建、列表、结果和下载不得构造评论分页客户端。只有 Supervisor 管理的人工补采 Worker 通过环境注入的 capability 调用固定评论分页 IPC。一次性脚本从正式代码中移除，避免任意本地脚本读取 capability 文件。

## Risks / Trade-offs

- [评论在分页期间变化] → 同一尝试按 `reply_id` 去重，记录实际处理数；不承诺平台不存在快照契约时的全局完全快照。
- [可重试失败重新读取全部评论] → 每次尝试先清空未发布结果并从零开始，优先保证结果无重复、计数正确与实现可推理。
- [命中评论长期落库] → 仅保存命中行，按创建者和活动游戏范围授权，禁止出现在通用 Job 参数/日志；保留期限或跨用户协作必须作为后续治理能力单独变更。
- [确认后帖子变化] → 创建时以不含个人信息的短时确认凭据重新读取并校验指纹，不一致时要求重新确认。
- [来源或会话不可用] → 复用既有 IPC 分类；会话恢复中延迟，来源契约/认证/业务删除等终态错误不发布结果。

## Migration Plan

1. 移除一次性脚本，收紧固定评论分页契约与测试。
2. 新增 Run/Result 模型、迁移、任务类型和人工补采 handler。
3. 实现三步工作区、任务列表、结果详情与数据库 CSV 流式导出。
4. 验证确认、规则、活动复用、重试重置、来源隔离、结果权限和导出不触及平台。
5. 回滚时停止认领新任务，隐藏未完成结果并回滚代码/迁移；已经成功保存的结果作为既有数据库数据处理，不通过回滚删除。

## Open Questions

- 无。V1 明确采用创建者隔离、结果长期保存与第一段连续数字；保留策略、删除能力和协作共享留给独立变更。
