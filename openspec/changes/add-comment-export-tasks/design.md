## Context

现有固定 `POSTS_LIST_TOPIC_REPLIES` 已验证：`cur_page` 是零基页码，平台稳定接受每页 100 条，`next_offset` 不能回填为页码。一次性脚本完成过单帖导出，但直接读取运行态 capability、将结果写文件且没有任务生命周期，不能演变为页面功能。

用户的新目标是结果数据化：运营人员不在完成时立即下载临时文件，而是在任务列表中查看持久化的命中结果，并按需从本地数据库导出。命中行仍包含正文、昵称与 OpenID，因此必须限制为创建者、当前游戏范围和已认证会话可访问。

## Goals / Non-Goals

**Goals:**

- 提供清晰的三步页面：确认帖子 → 配置规则 → 创建任务成功。
- 将完成任务的命中结果保存为可追溯数据库记录，支持任务列表查看与无需来源调用的 CSV 导出。
- 只在受管人工补采 Worker 中读取评论；页面不读取评论分页，不处理 capability 或 token。
- 对同一创建者的重复活动提交去重，且在重试后保持结果计数和结果行准确。

**Non-Goals:**

- 不保存不命中的评论、子回复、图片、头像、点赞、完整来源响应或认证材料。
- 不开放任意正则、任意脚本、任意 AppID/作者 OpenID/页大小输入，或跨帖批量导出。
- 不生成长期运行态 CSV 文件、每日清理 Job、自动评论任务或平台写操作。
- V1 不提供任务取消、跨用户共享结果或结果自动保留期限配置；结果作为运营任务记录长期保存，后续数据治理变更须单独设计。

## Decisions

### 1. 用一个无副作用的确认快照统一页面与创建

新增评论导出专用的**确认快照读取服务**。它是确认步骤和创建步骤唯一可用的帖子读取路径，返回经净化的标题、正文摘要、互动指标、作者昵称以及仅在服务端内存中使用的作者 OpenID、内容指纹和冻结范围；它不得写入 `OriginalPost`、`CandidatePost`、媒体、互动快照、Run 或 Job。不得复用会写本地帖子数据的 `classify_content_card`。

该服务在当前活动游戏的固定执行范围内按以下顺序运行：

1. 从本地 `OriginalPost` 按 `topic_id + source_appid` 读取已采集的 `content_id` 和作者 OpenID；两者缺失即拒绝确认。
2. 调用 `POSTS_GET_METRICS(topic_id)`，要求响应中的 `topic_id`、AppID 和 `creater.openid` 分别匹配请求帖子、当前活动游戏和本地作者；读取状态与互动指标。来源确认删除或任一身份不符均拒绝确认。
3. 调用 `POSTS_GET_CONTENT_CARD(content_id)`，从 `data.content_card` 提取内容。转发卡片、缺少 `base_content`、标题/正文类型无效均视为内容契约错误。正文规范化固定复用既有 HTML 转文本和尾部话题拆分规则；内容指纹为 `SHA-256(canonical JSON(title, normalized_content_text))`，不包含互动指标、作者昵称、媒体或本地缓存正文。

评论导出工作区使用可见步骤条和单一当前步骤，不将全部表单同时展开：

1. **确认帖子**：输入正整数帖子 ID，调用确认快照读取服务。成功才展示标题、正文摘要、阅读/点赞/评论指标和作者昵称；页面不显示 `content_id` 或作者 OpenID。
2. **配置规则**：确认成功才显示关键词输入和固定的“提取第一段连续数字”规则说明。
3. **创建任务**：提交短时确认凭据和规则；服务端再次调用同一确认快照读取服务，逐项验证范围、作者和内容指纹后创建或复用 Run 与 Job。成功后显示 Run 编号、初始状态和“前往任务列表”。

确认凭据有效期固定为十分钟，绑定签发它的用户；其签名载荷只含帖子 ID、来源 AppID、范围版本、内容指纹摘要、创建者 ID、签发/过期时间。签名用于完整性而非加密，因此页面只提交整枚确认凭据，不渲染或提交独立的内容指纹字段；摘要本身不是正文。凭据不得包含 OpenID、正文、`content_id`、token 或来源响应。若帖子已变化、确认超时、用户不一致或确认快照读取失败，服务端拒绝创建并要求重新执行第一步。

### 2. 规则为版本化的受限结构

V1 采用 `keyword-first-digit-v1`：关键词先去首尾空白并作 Unicode NFC 规范化，长度必须为 1--100 字符；评论正文同样作 NFC 规范化后，以区分大小写的字面子串匹配关键词，不作大小写折叠、分词或模糊匹配。命中评论还必须包含至少一段 ASCII 连续数字，提取正则固定为 `[0-9]+`，并导出第一段匹配；不得使用会匹配 Unicode 数字的 `\d`。结果行保留来源正文原文。来源 Unix 秒时间用 `Asia/Shanghai` 格式化为 `YYYY-MM-DD HH:mm:ss`。

规则版本、关键词和时区在 Run 中冻结。页面不允许输入正则或提取代码；若将来需要最长数字串、多个关键词或其它解析器，应创建新规则版本，不修改 V1 语义。

### 3. Run、Job 与结果行分层保存

新增 `CommentExportRun` 一对一关联 `BackgroundJob`，保存来源 AppID、冻结范围版本、帖子 ID、标题快照、作者 OpenID/昵称快照、规则、创建者和进度。新增 `CommentExportResult`，保存 `run`、`reply_id`、评论者 OpenID、昵称、创建时间、正文和提取数字；数据库唯一约束为 `(run, reply_id)`。

Run 是任务与权限边界，Result 是唯一导出数据源；`BackgroundJob.status=SUCCEEDED` 是唯一的结果发布标记。通用 `BackgroundJob.parameter_summary` 仅保存 Run ID 和执行范围版本，不保存关键词、作者 OpenID、正文或结果路径；结果列表与导出仅允许 Run 创建者在当前活动游戏的 AppID 等于 Run 来源 AppID 时访问。冻结范围版本只约束 Worker 的来源会话，不因之后切走游戏再切回而隐藏历史结果。V1 不共享他人 Run；活动去重键必须包含 `created_by`。

活动去重的唯一事实来源是既有 `enqueue_active_coalesced_job`。其 `active_coalescing_key` 固定为 `comment-export:v1:<sha256>`，摘要输入为规范 JSON 的创建者主键、来源 AppID、冻结范围版本、帖子 ID、作者 OpenID、规则版本和规范化关键词；不得把 OpenID 或关键词直接拼入 255 字符受限键。新 Job 的 `idempotency_key` 使用独立随机 UUID，不承担活动去重。单一外层数据库事务中：新建 Job 后创建一对一 Run，再将仅含 Run ID 和范围版本的参数摘要写回 Job；复用 Job 时反查其既有 Run。任一步失败必须回滚，不能遗留孤立 Job 或 Run。

选择结果行落库而不是最终 CSV 文件，是为了支持任务列表可查看、按需多次导出和避免文件保留/清理与数据库状态分叉。代价是持久化了命中评论；该范围通过只保存命中行、创建者隔离和后续独立数据治理能力控制。

### 4. Worker 每次尝试从零构建结果集

`COMMENT_EXPORT_V1` 只由人工补采 Worker 认领。Handler 使用冻结范围和作者 OpenID，固定调用 `POSTS_LIST_TOPIC_REPLIES(topic_id, topic_openid, page, limit=100)`，只读取顶层评论；下一页为 `page + 1`，不使用 `next_offset` 作为输入。

每个 Worker 执行尝试开始时，在一个短数据库事务中删除该 Run 的全部旧 Result 行并将 Run 进度与 Job checkpoint 重置为零。上游读取不得包在数据库事务中；每个成功解析的页面在独立短事务中批量写入命中 Result 并更新进度。Handler 读到末页且所有结果行持久化成功后直接返回；只有既有通用 Worker 随后将 Job 标记为 `SUCCEEDED`，结果才发布。页面、结果详情和 CSV 一律以 `Job=SUCCEEDED` 判断可见性，不读取独立的结果就绪字段。

Handler 必须用统一的 `try/finally` 覆盖整次尝试：只有所有页面都成功持久化并准备正常返回时才标记本次尝试完成；任何可捕获异常（包括来源、规则、分页、数据库或未预期程序异常）均在 `finally` 中以独立短事务删除该 Run 的全部 Result 并清零进度，然后按既有分类重新抛出。进程被强制中断而无法执行清理时，残留行因 Job 非成功不可见，并由恢复后的下一次尝试在开始时删除。这样终态失败也不长期保留部分命中评论。

每次尝试最多读取 10,000 页（最多 1,000,000 条原始顶层评论）。`has_next=true` 时页面不得为空，且必须至少包含一条此前未见的非空 `reply_id`；否则视为来源分页契约异常并终止本次 Job。该上限和重复页保护沿用已验证脚本的安全边界，防止来源异常导致人工补采 Worker 无限占用。

这比续写半成品和维护独立发布状态更简单，也避免动态页重叠、旧 checkpoint、结果可见性与 Job 成功状态分叉造成错误。代价是失败重试会重新读取该帖，但任务为单帖、每页固定 100 且同创建者活动任务去重，可接受。

### 5. 任务列表为唯一的结果查看和导出入口

创建成功后的页面只给出“前往任务列表”链接。任务列表默认仅显示当前用户、当前活动游戏 AppID 下的 Run，展示帖子、关键词、Job 状态、处理进度、命中数、创建/完成时间和固定失败摘要；Job 未成功的 Run 不显示结果行或导出按钮。

结果详情按 Run 分页显示已保存的命中行。CSV 下载端点从 `CommentExportResult` 按稳定顺序流式写出 `utf-8-sig`，字段严格为 `openid`、`nick_name`、`create_time`、`content`、`game_id`；不得读取平台、创建 Job 或保存文件。

### 6. 保持受控会话单向能力边界

Web 的确认与创建复核只可通过既有固定 `POSTS_GET_METRICS` 和 `POSTS_GET_CONTENT_CARD` IPC 调用完成；它们由服务端从当前活动游戏的本地帖子记录取得 `content_id`，浏览器不得提交该值。创建、列表、结果和下载不得构造评论分页客户端。只有 Supervisor 管理的人工补采 Worker 通过环境注入的 capability 调用固定评论分页 IPC。一次性脚本从正式代码中移除，避免任意本地脚本读取 capability 文件。

## Risks / Trade-offs

- [评论在分页期间变化] → 同一尝试按 `reply_id` 去重，记录实际处理数；不承诺平台不存在快照契约时的全局完全快照。
- [可重试失败重新读取全部评论] → 每次尝试先清空全部结果并从零开始；结果只在 Job 成功后可见，优先保证结果无重复、计数正确与实现可推理。
- [命中评论长期落库] → 仅保存命中行，按创建者和活动游戏范围授权，禁止出现在通用 Job 参数/日志；保留期限或跨用户协作必须作为后续治理能力单独变更。
- [确认后帖子变化] → 创建时以不含个人信息、绑定创建者且十分钟过期的确认凭据，重复调用指标与内容卡片接口校验指纹；不一致时要求重新确认。
- [评论分页异常或无限循环] → 固定 100 条页面、10,000 页上限以及“有下一页时必须有新增非空回复 ID”三重约束；违反即终止且不发布结果。
- [来源或会话不可用] → `SESSION_RECOVERING` 延迟且不消耗重试；`SOURCE_UNAVAILABLE` 与会话不可用走既有有限重试；`SOURCE_DELETED`、`SOURCE_CONTRACT`、分页/规则契约错误终态失败。所有失败均清理部分结果且不发布。

## Migration Plan

1. 移除一次性脚本，收紧固定评论分页契约与测试。
2. 新增 Run/Result 模型、迁移、任务类型和人工补采 handler。
3. 实现三步工作区、任务列表、结果详情与数据库 CSV 流式导出。
4. 验证确认、规则、活动复用、重试重置、来源隔离、结果权限和导出不触及平台。
5. 回滚时停止认领新任务，隐藏未完成结果并回滚代码/迁移；已经成功保存的结果作为既有数据库数据处理，不通过回滚删除。

## Open Questions
